# Membership deployment procedure

This is a technical operating procedure, not approval to deploy. The feature remains local, with test Stripe billing and captured account email. Public offerings, prices, benefits, imagery and terms are outside this cleanup. Passing preflight is configuration validation, not live readiness.

## Configuration checks

Use a supported current Node 22 runtime at least 22.13.0; managed Vercel Node 22.x must be checked on the actual deployment. Installed local Node 22.12 runs earlier checks but is below one ESLint dependency engine range. Install exactly the lockfile with `npm ci`; run repository lint, full TypeScript checks, all tests and the production build before staging a reviewed commit. Do not exclude failing tests from the build type scope. Never supply secrets to unreviewed branches or publish environment files, captured emails, browser storage or provider traces.

```sh
node --import tsx scripts/membership-preflight.ts local --env-file .env.local
node --import tsx scripts/membership-preflight.ts preview
node --import tsx scripts/membership-preflight.ts production
```

The last two commands read only the already configured process environment. An explicit `--env-file` is optional. The script returns configuration error names without values and contacts no services. It validates dedicated membership database/auth/job credentials, HTTPS and database TLS for hosted targets, Stripe mode and live gates, separate price IDs, positive capacities, and provider email rather than local capture for both hosted preview and production. It cannot prove price amounts, permissions, certificate validation, delivery, migration state, scheduler operation or provider readiness.

## Database and runtime

Select and authorize the production hosting project/domain and a PostgreSQL service/region. Configure a dedicated membership database or role with least required access and encrypted connectivity; match function region to the database and use a provider-supported pooled connection URL where appropriate. Verify actual TLS peer/certificate validation with that provider, then test connectivity from the staged runtime. The application uses `pg`, transactions and advisory locks and requires the Node.js runtime; it is not a static export. Configure backups, restore testing, access controls and retention before accepting member data.

Remote schema changes require separate authorization. Back up first, then run `npm run membership:migrate -- --allow-remote` against the explicitly chosen target using its private environment. The migration does not automatically load arbitrary production env files: inject the reviewed target variables in a secure shell or release job. Verify Better Auth tables, the application migration ledger, membership tables and both durable queues. Never run this command on production as part of an unapproved local build.

## Account email

Choose/authorize the sender domain and existing or new Resend account before provisioning or sending. Read-only inspection found the existing `blacktemple.dev` sending domain verified; this does not grant a sending credential or authorize outgoing mail. Validate the selected transactional sender and never substitute an unverified domain. Configure domain SPF/DKIM and an appropriate DMARC policy with the provider, verify the domain, then scope the sending API key to that domain. Set `MEMBERSHIP_EMAIL_MODE=resend`, `MEMBERSHIP_EMAIL_FROM`, `MEMBERSHIP_EMAIL_RESEND_API_KEY` and, only after outgoing-delivery authorization, `MEMBERSHIP_EMAIL_SEND_ENABLED=true`. Optionally set `MEMBERSHIP_EMAIL_REPLY_TO`. Store these only in protected runtime settings. `BETTER_AUTH_SECRET` protects account tokens and encrypted queued email; rotate it only with a deliberate session/queue invalidation procedure.

Local checks use `MEMBERSHIP_EMAIL_MODE=capture`, loopback auth/database and a private absolute `MEMBERSHIP_EMAIL_CAPTURE_DIR` outside `public`, `.next` and `out`; captured verification/reset links are credentials and must not be published. Hosted previews cannot use capture. They require separately approved Resend delivery with sender/key and `MEMBERSHIP_EMAIL_SEND_ENABLED=true`, while retaining Stripe test mode and disabled live billing. If outgoing delivery is not approved, hosted-preview preflight correctly fails and local capture verification continues. Confirm actual verification and reset delivery to an authorized test mailbox, expired/reused token rejection, enumeration resistance, redirects, session invalidation and database-backed rate limiting in staging before public launch. Provider email failures require monitored queue retries, not a silent capture fallback.

## Stripe and recovery scheduling

Create/review the three *live* monthly USD prices only with authorization, preserving $20/$100/$1,000 and the existing finite three-payment schedule. Test price IDs cannot be reused as live IDs. Verify recurring interval `month`, interval count one, currency `usd`, amounts 2000/10000/100000 cents and the intended account. Keep `MEMBERSHIP_CHECKOUT_ENABLED=false` during setup.

Create the HTTPS endpoint `/api/membership/webhook` in the intended Stripe account/mode and privately configure its endpoint signing secret, which differs from a Stripe CLI listener secret. Subscribe to: `checkout.session.completed`, `checkout.session.expired`, `customer.subscription.created`, `customer.subscription.updated`, `customer.subscription.deleted`, `invoice.paid`, `invoice.payment_failed`, `invoice.payment_action_required`, `invoice.finalized`, `subscription_schedule.completed`, `subscription_schedule.canceled`, `subscription_schedule.released`, `charge.refunded`, `charge.dispute.created`, `charge.dispute.closed`. Review API-version compatibility with the pinned SDK and integration tests. Verify signatures, duplicate/reordered delivery and replay recovery on the hosted sandbox before live activation.

Provision an authorized scheduler that calls `GET /api/membership/process` every minute with `Authorization: Bearer <MEMBERSHIP_JOB_SECRET>` from a secret store, or implement/review a supervised production worker. The existing `membership:worker` CLI intentionally rejects remote databases and live billing: it is not the production worker command. The recovery hook now accepts either explicitly configured `MEMBERSHIP_JOB_SECRET` or `CRON_SECRET` through a reusable fixed-length constant-time digest comparison. No secret is generated and no cron is activated; configuring `CRON_SECRET` alone does not establish scheduling. Confirm plan cadence supports the intended interval. No active `vercel.json` cron or deployment pipeline is added here.

The webhook enqueues durably and `after()` makes a best-effort processing attempt within its 60-second route budget. The scheduler must continue retries independently of incoming traffic. Monitor pending-job age/count, expired leases, repeated failures, provider webhook failures, email retry failures and scheduler errors; set alerts to an agreed operator. Load-test queue drain throughput and concurrent invocations, verify no duplicate delivery/charges, and deliberately stop/restart processing to prove recovery. Do not infer scheduler operation from successful static preflight.

## Release boundary

After explicit production setup approval, stage a reviewed production build without assigning the public domain, test that exact deployment and its sandbox configuration, and promote only the tested build after release approval. Avoid an automatic push-to-production workflow before approval; no CI credentials or hosting grants are established by this procedure. Verify logged-out access, account flows, origin checks, ownership, finite billing regressions, cache/noindex behavior, database migrations and recovery scheduling on the target runtime.

Live billing is a separate approval: `MEMBERSHIP_BILLING_MODE=live`, `MEMBERSHIP_LIVE_ENABLED=true`, `VERCEL_ENV=production`, matching live key/prices/webhook, and finally `MEMBERSHIP_CHECKOUT_ENABLED=true`. Production preflight can pass for a staged test-billing configuration; its output explicitly says that test mode is not live billing readiness. No real-card/live charge is authorized by the technical cleanup. User review of offerings, policies and actual member content remains a launch prerequisite.

Official references reviewed: [Next.js self-hosting](https://nextjs.org/docs/app/guides/self-hosting), [Next.js after](https://nextjs.org/docs/app/api-reference/functions/after), [Stripe webhooks](https://docs.stripe.com/webhooks), [Vercel Cron](https://vercel.com/docs/cron-jobs), [Vercel staged promotion](https://vercel.com/docs/deployments/promoting-a-deployment).

## Protected sandbox and zero-cost recovery

The user authorized a protected hosted sandbox with zero additional spend. External provisioning/deployment remains paused until zero incremental cost is established for the exact existing accounts, plans, usage/quota and selected action, and credential/access use is approved at action time. A plan advertised as free does not prove zero incremental cost; compute, database, email and bandwidth usage can still trigger overages. Public URLs, protection bypass credentials and deployment access must be reviewed before use.

The authenticated `/api/membership/process` endpoint accepts only configured job/cron bearer secrets, returns private/no-store responses, and exposes aggregate queue health: pending/ready/processing counts, expired leases, terminal failures, retrying count and oldest pending age. It never returns job IDs, users, email addresses, tokens, payloads or stored error strings. Requests marked `X-Membership-Recovery-Mode: sandbox` are rejected before mutation when billing is not test, live is enabled or the runtime is not explicitly `VERCEL_ENV=preview`. Each request starts at most 20 work items within a 20-second scheduling budget; an in-flight provider operation may extend beyond that budget, bounded by provider/route timeouts. Monitor repeated failures and backlog age rather than treating a successful HTTP response as successful delivery.

A local manual alternative is `node --import tsx scripts/membership-recovery.ts`, with no dotenv loading or automatic activation. Supply private process environment only after action-time approval: exact `MEMBERSHIP_RECOVERY_ORIGIN=https://<approved-protected-staging-host>` (origin only, no credentials/path/query/fragment), `MEMBERSHIP_RECOVERY_APPROVED=true`, `MEMBERSHIP_RECOVERY_TARGET_ENV=preview`, `MEMBERSHIP_BILLING_MODE=test`, and the existing `MEMBERSHIP_JOB_SECRET`. If protection requires it, provide `VERCEL_AUTOMATION_BYPASS_SECRET` in the private environment; it is sent only as the platform bypass header to that exact origin. The runner fixes `/api/membership/process`, rejects HTTP redirects, requires explicit test-billing and preview-runtime response confirmation and prints only numeric allowlisted health fields. It was tested with an injected local fake transport; it has not been run against a remote deployment.

Defaults are one invocation. Optional `MEMBERSHIP_RECOVERY_INVOCATIONS` is bounded to 1–20, `MEMBERSHIP_RECOVERY_INTERVAL_SECONDS` to 60–1200, and `MEMBERSHIP_RECOVERY_TIMEBOX_SECONDS` to 1–1200. Repeated invocations are at least 60 seconds apart; each request times out at most after 55 seconds and the runner stops when its timebox expires. This alternative adds no scheduler subscription but target/provider work can consume existing quotas, so zero incremental spend must be confirmed first. A manually run, bounded recovery session is not continuous monitoring, automatic email retry coverage or a launch-ready scheduler. No cron or supervised production worker is enabled by these local changes.

## Protected sandbox preparation on 2026-10-09

The user approved a protected hosted sandbox using existing accounts with zero additional spending and verification/reset mail only to the explicitly approved inbox. This does not waive action-time approval for new credentials or persistent access. Hosted preview preflight now requires explicit `MEMBERSHIP_STAGING_MODE=true` and one `MEMBERSHIP_EMAIL_ALLOWED_RECIPIENT`; auth enrollment and delivery reject other recipients. Missing preview restriction configuration fails closed. Public offers, terms and imagery are unchanged.

Current read-only evidence confirms active Vercel Pro, Neon Free installation `free_v3`, and unused Resend transactional quota (0/100 daily, 0/3000 monthly). Vercel current-period usage is below its published included credit, but exact zero incremental billing enforcement was not established; no upgrade, paid resource, deployment, cron, credential or outgoing mail was created. The bounded runner has no scheduler subscription but invokes metered hosted work and therefore is not an automatic zero-cost guarantee.

Vercel automation bypass credentials apply to all deployments in their project. A separate protected sandbox project in the existing team is the preferred minimal-access proposal; creating its access and credentials requires confirmation. Do not configure a bypass across the existing production project or disable its protection silently. Neon isolation should use a new independent Free sandbox resource, with no production-data clone or connection, and a reviewed least-privilege role. Resend should use a sending-only domain-scoped key. Store secrets privately; never paste them into chat.

All 57 repository tests, full lint/type checking and the final local webpack build passed. The build blocked external fetches to avoid production transfer/data usage; existing social previews used fallbacks. Account integration passed against that final local build using private captures with zero outgoing messages.
